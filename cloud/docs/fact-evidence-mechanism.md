# 事实层证据机制（Fact-Evidence Mechanism）

> 上位契约：`north-star-constitution.md`（A2 宁空不假、A3 机制优先）；落地绑定见 `mechanism-master-v4.md`。
> 解决的根因：把**连锁规模**与**中央厨房/预制/食安**混为一谈，且词表规则无证据裸断言硬标签。
> 确立于 2026-10-01。

## 一、第一原则：四条独立轴，禁止互相推断

| 轴 | 字段 | 回答的问题 | 取值 |
|---|---|---|---|
| ① 规模轴 | `chain_type` | 开了多少店、是否资本化 | 独立店 / 小型连锁 / 大型连锁 / 资本化连锁 |
| ② 工艺轴 | `central_kitchen` | 是否由中央厨房集中加工 | 无 / 疑似 / 确认 |
| ③ 出品轴 | `premade_risk` | 到嘴的菜多大比例是预制/料包 | 无 / 低 / 疑似 / 高 |
| ④ 安全轴 | `food_safety` | 是否有权威食安通报 | 无 / 疑似 / 确认 |

**铁律：**
1. **连锁 ≠ 中央厨房/预制。** 大型连锁可以门店现做：丸龟制面（每店制面机、不建中央厨房）、费大厨（明档现切现炒、不做中央厨房）、Manner（半自动、咖啡师现场制作，自建的是咖啡豆烘焙厂）、星巴克臻选烘焙工坊（店内现场烘焙）。
2. **独立店也可能用预制。** 规模轴与工艺/出品轴**只能各自取证、各自标注**，禁止从一个轴推断另一个轴。
3. **烘焙厂 ≠ 餐食中央厨房。** 咖啡品牌的豆烘焙厂属于原料加工，不构成"预制菜中央厨房"。
4. **委托加工/半成品配送 ≠ 自建中央厨房。** 证据只支持"委托加工+配送中心"时，`central_kitchen` 至多定**疑似**（如外婆家）。

## 二、第二原则：硬标签必须有证据，词表只产生候选

- **硬标签** = `central_kitchen=确认`、`premade_risk=高`、`food_safety=确认/疑似`。
- 硬标签**必须**在 `fact_claims` 中存在「同 `type` 且带 `source_url`」的主张；否则禁止落库。
- 规则/词表（`negative_audit.PREMADE_EXTRA` 等）命中后**只产生候选**：未经取证一律封顶为 `central_kitchen=疑似`、`premade_risk=疑似`；硬标签晋升必须经证据。
- 证据等级：
  - **权威源（可直接定硬标签）**：政府市监通报、招股书/年报、官网供应链介绍、官方媒体调查。
  - **单源/品牌自述（至多疑似或反向）**：品牌"现炒"自述、加盟招商页、UGC 单条。
  - 食安问题一律以**市监通报**为准并标日期；非本地门店/非堂食业务线只定**疑似**。

## 三、流水线（候选 → 取证 → 闸门 → 回写 → 复验）

```
规则/词表命中 ──► 候选(封顶疑似) 落 review 文件        [negative_audit.py，不直接给硬标签]
                        │
品牌归并(同品牌多门店合并) ──► 待取证品牌清单
                        │
模型+搜索取证：逐品牌 general_search(中央厨房/预制/供应链/食安)
                        │
              结论+source_url+quote ──► claims_seed.json   [只改数据不改代码]
                        │
fact_verify.py ──► 品牌→门店匹配 / 值域校验 / claims 合并去重 / 幂等 PATCH / 写后回读
                        │
fact_evidence_gap.py ──► 质量门：硬标签无证据即报缺口(--strict exit 1)
                        │
              字段保鲜到期 ──► 重新取证复验（见下）
```

- **新增/修正事实只改 `claims_seed.json`，不改代码**；机械环节（匹配/校验/去重/幂等写/回读）全部脚本化。
- 同店异写、近名异店、同名异址分店的处理见 `entity-verification.md`（同名异址分店保留）。

## 四、模块与闸门绑定（spec→code）

| 能力 | 模块 | 状态/账本 | 闸门/节奏 |
|---|---|---|---|
| 候选产生（词表封顶疑似） | `negative_audit.py` | negative_plan.json | 写时/每周 |
| 事实取证种子 | `claims_seed.json`（模型+搜索） | /app/data/fact_verify | 取证即更新 |
| 机械写库+回读 | `fact_verify.py` | fact_claims | --apply |
| **硬标签证据门** | `fact_evidence_gap.py` | fact_evidence_gap.json | release_audit / 发版 |
| 字段保鲜 | freshness_due / data_updated_at | 到期重验 | 90/180 天 |

> `fact_evidence_gap.py` 应被 `release_audit.py` 串联：硬标签证据缺口 > 0 时 A–H 扫描不通过、不发版。

## 五、前端筛选语义（恢复 FE 时遵循）

- **「隐藏连锁」按规模轴 `chain_type != 独立店` 过滤**，不得用 `is_chain_standardized`（工艺轴），否则费大厨这类"连锁但现做"会漏、而工业化非连锁会错。
- **「去工业化/预制」按工艺/出品轴**（central_kitchen / premade_risk / is_chain_standardized）过滤。
- 两个筛选相互独立、可叠加。

## 六、反模式（禁止再犯）

1. 词表命中即写 `确认/高`，无 source_url。
2. 因"是连锁"直接推断中央厨房/预制（丸龟、费大厨教训）。
3. 把咖啡豆烘焙厂、店内烘焙工坊误判为预制中央厨房。
4. 凭单条工业评论/单条 UGC 直接定硬标签（权威多源确认才可）。
5. 委托加工/半成品配送证据却写"自建中央厨房=确认"。
