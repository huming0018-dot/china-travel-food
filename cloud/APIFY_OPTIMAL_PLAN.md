# Apify 采集最优方案（Optimal Apify Collection Plan）

> 任务 #44：优化 Apify 采集方案，**以"完成采集目标"为结果**输出最优方案。
> 上位契约：`north-star-constitution.md`（口味唯一最高、宁空不假、机制优先、信源沉淀、账号最后手段、闭环自检）。
> 版本：v1，2026-10-02，采集运维（collector）窗口。
> 本文所有数字均来自实读：Apify 账单 API + 全量 539 次运行聚合 + 控制器日志 + 一次 toolzerhub 探针。

## 0. 采集目标（完成判据，先定义"完成"）

对 `worth_fill` 允许集中**每一家真实、在营、非连锁标准化的独立/优质餐厅**，满足二者之一：

1. **达标**：拥有 `need=2` 条 `is_verified_diner=true`、`trust∈{mid,high}`、带真实口味信号的堂食评价；或
2. **判为"公开 UGC 不可补"**：走完查询阶梯（q1→q2）仍 0 采信，进入 `deferred` 并写明原因（如私房/预约制/无公开食客帖）。

残余店必须**显式上报**，不静默丢弃。口味是唯一准入轴：**合集/盘点、官方通稿、媒体稿一律不计为口味证据**；电话/坐标/营业时间等其他字段不动。

> 不追求"每家都有 2 条"，追求"该有的真实口味证据一家不缺、补不到的有明确交代"。

## 2. 最优方案：先免费缩分母，再按"每店封顶 + 持久熔断 + 查询阶梯"付费补残余

### 2.1 总原则（成本最优的次序）
```
免费通道扫一遍 → 重新生成 worth_fill（缩分母）
   → 对真残余跑 Apify：每店最多 2 次（q1→q2）
   → 达 need=2 即停；2 次仍 0 → deferred 上报
   → 全局持久熔断 + 日预算闸门，杜绝爆发式烧钱
```
> 关键：Apify 只补"免费通道之后的真残余"，且任何店在一个月度周期内最多烧 2 次。

### 2.2 分母最小化（L0/L1 优先，A5 账号最后手段）
- 先并齐**免费/签名通道**：高德（已产 921 条）、腾讯、存量小红书；以及后续 wechat/douyin 连接器（其他任务）。
- 每轮付费前**重新生成 `worth_fill.json`**（prefill_governance 已建，当前 986=924 独立+62 优质），把已从免费渠道获得 ≥2 口味证据的店移出付费队列。
- 控制器每次启动重读 worth_fill（已实现 via `worth_ids`）。

### 2.3 每店尝试台账 + 封顶（治失控重跑，最高优先级）
- state 增 `attempts: {rid: {n, kws, last, cycle}}` 与 `deferred: [{id,name,reason}]`。
- **每店每周期最多 `MAX_SHOP_ATTEMPTS=2` 次**；达到上限仍 <need → 转 `deferred`（写明：合集主导/无口味/跑题/私厨无公开帖），本周期不再选入。
- `select_targets` 同时排除：已达 need、连锁标准化（已实现）、**本周期 attempts 达上限/deferred**。
- 月度额度重置后清空 attempts，给 q 策略更新后的二次机会。

### 2.4 查询阶梯（q1→q2，治名店合集）
- **q1**：`{base} {branch_hint} 上海`（现状）。
- q1 若**合集占比高或 0 采信** → **q2**：`{base} {branch_hint} {dish_hint} 堂食 测评`
  - `dish_hint` 取该店 `signature_dishes` 中一个具体招牌菜，或菜系叶子词；
  - 加「堂食/测评」、用具体菜名，可**绕开合集**、召回单店食客帖。
- 大品牌（连锁规模大/合集高发）可**直接从 q2 起步**，省一次裸搜。
- 英文名/别名 + 商圈作为 q2 的另一可选拼法。

### 2.5 合集不浪费：转入发现队列（服务深覆盖）
- 合集帖含多家真实店与简短 verdict，是**覆盖扩容**资产（对应 F4/F6 与深覆盖目标）。
- 一次 run 里的合集帖统一写入 `roundup_queue`（url + 正文 + 提到的店名），交由发现/覆盖模块后续挖掘；**不计为被搜店的口味证据**（现状正确）。
- 本任务只负责**捕获入队**，完整挖掘器列为后续（见 HANDOFF）。

### 2.6 持久全局熔断（补 v2 外层重启缺口）
- state 增 `circuit: {open_at, reason, provider, cooldown_until}`。
- preflight 双确认触发即**持久化**；外层控制器**跑脚本前先查 circuit**：开启且在冷却内（初始 `CIRCUIT_COOLDOWN=3h`）→ 完全不跑。
- 冷却后只放 **1 个确认探针**；仍 0 采信 → 重新熔断并**指数退避**（3h→6h→12h→24h）。
- **熔断判据要区分性质**，避免误杀：
  - 高锚定但 0 口味 / 合集主导 → **查询问题 → 走 q2**，不熔断；
  - 0 锚定 / 大量跑题（well-formed query 下）→ **actor 相关性问题 → 熔断**。

### 2.7 成本路由（默认 opspilot）
- 默认 **opspilot（$0.10，质量稳）**；实测普通店 1 run 即 ≥2 采信（首批 6 店采 15 条，2.5/店）。
- toolzerhub 探针（`Tacolicious 上海`）：9 条 0 采信（5 跑题/2 合集/2 无口味），且一次失败仍需 opspilot（$0.021+$0.10=$0.121 > $0.10 直跑）→ **不进默认链路**；仅保留为后续大样本再评估对象。
- atomus/zenstudio（$0.17）仅备用；禁用 $1.97/$0.36 的高价 actor（加入禁选）。
- 保留 `maxTotalChargeUsd=0.30`、opspilot `memory=512`。

### 2.8 日预算闸门（把月度上限摊平，根治"月初一天烧光"）
- 每日允许花费 `daily_allow = remaining_credit / 当月剩余天数`（设地板/上限），当日增量到顶即停、睡到次日。
- 与每店封顶、持久熔断叠加为三重护栏；账单 API 为**权威门**，内部估算仅作次级兜底。

### 2.9 主机 notifier 修复（告警不再丢/不再刷屏）
- 脚本内告警改为 `_notify(level,key,body)`：先尝试 `import notifier`；失败则追加一行到主机 `alert_queue.jsonl`。
- 外层控制器每次脚本结束后**排空 `alert_queue.jsonl`**，经 `docker exec` 的 NOTIFY（唯一可用投递通道）转发，然后清空 —— 恰好一次。
- **额度耗尽**：只发 **1 条 `action`**（按 nudge 节奏，如 24h 一次），随后**长睡 `CREDIT_WAIT=4h`** 再评估；仅当额度状态变化（到账后又耗尽）或节奏到点才再发，**不再每 20 分钟 warn**。

### 2.10 dry-run 改为真·离线
- 非 `--apply`（默认）**不调用付费 API**，只输出：目标清单、每店将发的 q1/q2、attempts/circuit/日预算状态。需要真实抓取时显式 `--fetch`（或直接由控制器带凭据跑）。

## 3. 完成采集的预算与节奏（Completion Math）

- 当前残余 **944 店**（免费通道扫完 + 合集挖掘后会下降）。
- runs/店：普通店 ~1，合集高发/难店最多 2 → 平均按 **~1.25** 估。
- 毛费（分母不变的最坏情况）：944 × 1.25 × $0.10 ≈ **$118**；免费通道缩分母后更可能落在 **600–800 runs ≈ $60–80**。

| 方案 | 做法 | 周期 | 成本 |
|---|---|---|---|
| **A 稳态省钱（推荐起步）** | 先免费扫+重算 worth_fill，部署全部护栏；维持 $40/月，日预算摊平（~300–350 店/月） | ~2–3 个月 | ~$40/月 |
| **B 一个周期内完成（最快）** | 在 A 的护栏基础上，一次性充值/上调平台月度上限至 ~$100–120 | ~1 个月 | 一次性 ~$80–120 |
| **C 极限压缩** | 尽量用免费/签名/官方与地图通道，Apify 只补最硬残余 | 视通道建设 | 现金最低，但依赖其他连接器落地 |

> 建议：**先做 C 的免费缩分母 + 落地全部护栏（不花钱），再据缩小后的真残余在 A/B 间拍板预算。** 支付始终由本人完成。
