## 0. TL;DR（先看结论）

1. **数据层比应用层成熟**：002 硬化（CHECK/触发器/唯一索引/审计视图/RLS）已经把"非法数据写不进、关店/评分/坐标自动兜底"做对了；但**采集端的"结构性覆盖"没有质量门**，这是日料深、其他菜系浅/薄的根因（已用 stage6 量化，并已固化为 skill + 新脚本，见第 7 节）。
2. **应用层有 1 个 P0 数据安全定时炸弹**：GitHub Actions 每天跑旧的"飞书→Supabase 全量同步"脚本，该脚本依赖 GitHub runner 上不存在的 `lark-cli`（现在必然失败），但**一旦环境被修好，会用写死的旧飞书表 `--full` 覆盖/删除现网精修数据**，且与 Vercel Cron 的新版只读 `/api/sync` 同名并存。建议立即停用。
3. **零自动化测试、零 CI 校验**：tsconfig 虽开 strict，但没有任何测试框架、lint 依赖、构建门禁；前端分类树硬编码、首屏全量拉取三表、数据库已建好的 `search_vector` 完全没被使用。
4. **本地有 27 个一次性脚本明文写了 service role JWT**（好消息：经核实它们**都未被 git 跟踪、未进 GitHub**；被跟踪的 4 个脚本均干净）。仍建议轮换密钥并清理，因为明文散落在桌面工作区，误分享/误提交即泄露超级密钥。
5. 用户此前提的 6 类产品问题（漏店、误分类、关店不更新、标签筛不了、地址定位、打卡评价）中，**关店/地图/UGC/标签**已在数据层和前端基本补齐；**漏店与覆盖深度、分类数据治理、搜索体验**仍未根治，需要靠升级后的采集管线 + stage6 回扫系统性解决，而不是逐店打补丁。

成熟度初判：**数据建模 B+、采集方法论 B（已修，待执行验证）、前端 C+、工程化/测试 D、安全运维 C-**。

## 1. 产品经理视角（PM）

### 1.1 产品定位与价值闭环
- 核心价值主张成立且差异化清晰：**反软广、可溯源堂食证据、按食客地图认知分类**的上海美食数据库。这是相对大众点评/小红书的护城河，不能在迭代中被"榜单/人均排序"稀释。
- 价值闭环当前断点在**数据供给的一致性**：日料样板证明了方法论能产出高可信结果，但同一方法论没有被机制化地强制套用到每个菜系，导致用户"抽样川菜就觉得和点评没区别"。**产品最大的风险不是功能少，而是信任不一致**——用户只要在一个菜系踩到软广/浅数据，就会怀疑整个库。

### 1.2 用户已提 6 大问题的闭环状态
| # | 用户问题 | 现状（实测） | 状态 |
|---|---|---|---|
| 1 | 漏店（nabi/jelu/yaya's/nono's；甜品咖啡 brunch bistro 缺得多） | 场景类店按"菜系"扫必然漏；data-pipeline §2.1 已要求按场景垂直独立扫，但**无覆盖门**保证执行到位；stage6 已能暴露薄格 | 机制已补，**待回采验证** |
| 2 | 分类错误（荣府宴误归本帮菜） | 已建品牌系交叉比对 SOP（lessons 18）、`brand_group/brand_confirmed` 字段；荣府宴类问题靠采集时核实，**缺全库品牌系回扫** | 单点已修，**未全量治理** |
| 3 | 过时信息（EHB 关店仍展示、人均错） | status=closed 三要素、`v_data_freshness` 保鲜视图、前端默认隐藏关店均已就位；EHB(id1262)/CHIC1699(id905) 已 closed | **基本闭环**，需周期巡检常态化 |

### 1.3 信息架构与可发现性
- 二级/三级菜单、场景根（正餐/快餐/甜品/饮料）、正交特别标签的方向用户已认可；但**分类树同时硬编码在前端**（`restaurants/index.tsx` L15-19 的 `CUISINE_TABS/EIGHT_GREAT/FORMAT_GROUPS/TIERS`）和数据库 `cuisines` 里，两处真相会漂移——加一个菜系或改一个归类要改代码并重新部署，运营无法自助。
- 搜索框只在**已全量下载到浏览器的店**里做 `name/address/business_area/signature_dishes` 子串匹配（index.tsx L240-248），不搜英文名、菜系/品类名，也没有用数据库已建好的 `search_vector`。用户搜"omakase""烧鸟""新荣记"这类词命中率没有保障。

### 1.4 PM 视角优先级（MoSCoW）
- **Must**：停用危险旧同步（P0）；按升级后管线 + stage6 把菜系覆盖做齐做深（信任根基）；分类树改为数据库单一数据源。
- **Should**：服务端搜索（消费 search_vector，覆盖英文名/菜系/招牌菜）；品牌系全库回扫；UGC 举报/审核与"写评价"入口引导。
- **Could**：收藏/清单、按画像（商务/老饕/家庭）的场景推荐、菜品/单品价格对比页、数据新鲜度与覆盖度的公开"运营看板"。
- **Won't（本期不做）**：外卖/交易、商家自助认领后台（先把内容信任做厚）。

## 2. 第三方测试视角（QA）

### 2.1 测试现状（实测，偏薄弱）
- 全仓库 `*.test.* / *.spec.*` 文件数 = **0**；`package.json` devDependencies 无 jest/vitest/playwright，**也没有 eslint 依赖**（虽有 `lint` 脚本）；GitHub Actions 只有一个同步工作流，**没有任何 build/lint/test 门禁**。
- 也就是说：TypeScript `strict: true` 是目前唯一的静态防线；页面能不能渲染、筛选对不对、写库会不会炸，全靠人工点。

### 2.2 风险清单（按可观测性排序）
| 风险 | 触发条件 | 后果 | 当前是否有自动拦截 |
|---|---|---|---|
| 旧飞书全量同步覆盖现网 | Actions runner 一旦具备 lark-cli / 改自托管 | 现网 987 家精修数据被旧表覆盖或删除（脚本含"清理旧数据"、写旧 status 口径"推荐"） | **无**，且与新 cron 并存 |
| 回归不可知 | 任何前端/写库改动 | 筛选漏店、详情崩溃、写库 500 无法提前发现 | 无测试，靠人工 |
| 数据结构回归 | 改采集/写库 | 悬挂关联、重复店、越界坐标、评分口径漂移 | **有**（002 约束 + stage4/stage6，最成熟的一块） |
| 密钥泄露 | 误提交/分享工作区/截图 | service role 可绕过 RLS 全库读写 | .env 已 ignore；但 27 个本地明文脚本无防护 |
| 部署物不可复现 | .next 入库、手跑 DDL | 合并冲突、环境间 schema 漂移、无法回滚 | 无 supabase CLI、无迁移流水线 |
| 采集"看似完成" | 子代理自报完成 | 空格/薄格/薄证据被当成交付 | stage6 上线前=无；上线后可量化拦截 |

### 2.3 建议的最小质量体系（金字塔，自下而上）
1. **数据层（最高性价比，大部分已具备）**：002 的 CHECK/触发器/唯一索引继续作为硬门禁；`stage4_audit.py`（单店微观）+ `stage6_coverage.py`（结构宏观）作为采集任务的**强制退出码门禁**（`--strict`），不达标不许标记菜系完工。
2. **脚本单测/契约测试**：对 `common.py`（tier 换算、电话清洗、坐标解析、归一去重）和 stage1 校验器加少量 pytest 黄金样例（含"菜品名≠餐厅""假电话尾号7777""GeoJSON 必须被拒"这些真实踩过的反例）。
3. **API 冒烟**：一个脚本对生产 URL 断言 `/restaurants` 关键查询、`/api/sync` 无密钥 401/有密钥 200、关店店不出现在列表。
4. **前端关键路径 E2E（Playwright，3-5 条即可）**：打开首页→按菜系+档位筛选出店→搜索命中→详情页地图/标签渲染→登录→写评价。放进 CI，PR 必跑 `next build` + 这些用例。

### 2.4 交付验收清单（建议每个菜系/每次发版照单核对）
- stage4：ERROR=0；硬伤类（越界/越档/关店三要素/重复/评分越界）=0。
- stage6：无空格（稀缺格已标注）、薄格率<20%、薄证据店（<200字）<10%。
- 抽样 5 家：证据可溯源（≥2 条含菜名点评、≥2 类渠道）、品牌系归类正确、地址电话可拨通/可导航。
- 前端 E2E 全绿；生产 URL 冒烟通过；变更项有回滚路径。

## 3. 工程师视角（ENG）

### 3.1 现状架构
```
浏览器(PWA, Next14 Pages)
  └─ 首屏一次性分页拉全量 restaurants(全列)+cuisines+restaurant_cuisines(6503)
       └─ 客户端内存筛选/排序/分页(PAGE=120)、客户端子串搜索(未用 search_vector)
            └─ Supabase(anon key, 公开 SELECT；RLS 无写策略)
                 ├─ 表 restaurants/cuisines/restaurant_cuisines/reviews
                 ├─ 002: 触发器派生 tier/total/search_vector + CHECK + 唯一索引 + 审计视图
                 └─ 写：仅 service_role（管线 stage3 REST 或 upsert_restaurant RPC）
采集侧（本地/skill，不在线上）：模型 browser-use 取证 → raw.jsonl → stage1..6 脚本
同步侧（两套并存，冲突）：
  ① GitHub Actions 每天 03:00UTC 跑旧 sync_feishu_to_supabase.py --full（危险，见 P0-1）
  ② Vercel Cron 每天 03:00UTC 调 /api/sync（只读体检+心跳，安全）
```

### 3.2 P0 — 安全与数据安全
- **P0-1 双同步冲突 / 旧全量同步是定时炸弹**（证据：`.github/workflows/sync.yml`、`scripts/sync_feishu_to_supabase.py`）
  - workflow 在 `ubuntu-latest` 上只 `pip install supabase pandas`，却用 `subprocess` 调 `lark-cli sheets +csv-get`（L20/L150-160）——runner 上没有 lark-cli，此步今天必然失败；
  - 脚本写死 3 个旧飞书表 token（菜系大全 + 日料黄页 + 中餐黄页），含"清理旧数据"DELETE（L288 附近）与旧 status 口径"推荐"（L349，现库 status 仅 active/closed）；
  - 与 Vercel Cron 的 `/api/sync`（只读、绝不改 status、强制 CRON_SECRET）**职责同名、时刻相同**。
  - 处置（需你确认，属高影响写操作）：停用/删除该 workflow 与 `npm run sync`，数据采集统一走 skill 管线；若要保留"飞书作为编辑入口"，则重写为**只追加/按主键合并、不删除、不覆盖精修字段、且在受控环境带 lark-cli**的单向同步，并与 /api/sync 改名区分。
- **P0-2 本地 27 个脚本明文 service role JWT**（实测：14 个根目录 `integrate_*.py` + `data_subagent_work/*` + `scripts/step*.py`）
  - 已核实**均未被 git 跟踪**（被跟踪的 4 个 py 全部干净），所以**没有经 GitHub 泄露**；`.env*.local` 也已 ignore。
  - 但明文散落桌面工作区，风险来自误提交、分享文件夹、屏幕共享、备份同步。建议：① 在 Supabase 轮换 service role key（会牵连 Vercel env 与本地 `app/.env.local`，需同步更新）；② 删除这 27 个一次性脚本或迁入不带密钥的归档（统一改用 `food_pipeline/common.py` 从 env 读 key）；③ 给仓库加 pre-commit 密钥扫描（gitleaks）。
- **P0-3 `.next` 构建产物 89 个文件被 git 跟踪**（`.gitignore` 虽有 `/.next/`、`app/.next/`，但对已跟踪文件无效）。处置：`git rm -r --cached` 对应 `.next` 后提交，避免构建产物污染 diff/冲突。

### 3.3 P1 — 性能、可扩展性、可维护性
- **P1-1 首屏全量拉取 + 前端筛选**（index.tsx L26-43、L63-75、L236-263）：店数到数千、评价/图片字段增多后，首屏体积与低端机内存会成为瓶颈；匿名 key 也等于把全库可枚举。建议改为服务端/`@supabase/postgrest` 带条件的分页查询（按当前筛选下推到 RPC 或视图 `v_restaurant_enriched`），前端只持有当前页。
- **P1-2 搜索没用 `search_vector`**：002 已维护 A 店名/英文名、B 商圈/区、C 地址的全文向量，前端却纯子串匹配。建议提供 `/api/restaurants?q=`（Postgres `tsvector`/`websearch_to_tsquery` 或简单 `ilike` 多列 + 菜系名展开），支持英文名、菜系、品类、招牌菜，并做服务端限流。
- **P1-3 分类树硬编码前端**（L15-19）：改为从 `cuisines` 表按 `dimension/parent_category` 动态渲染导航树（数据库已是唯一权威），运营加菜系无需发版；前端只保留展示顺序/图标等少量配置。
- **P1-4 无 supabase CLI、DDL 靠 Dashboard 手跑**：`db/migrations/001/002.sql` 在仓库但没有迁移状态/环境隔离/回滚。建议引入 supabase CLI（`supabase/config.toml` + migrations），本地/生产迁移可重放、code review 覆盖 schema 变更。
- **P1-5 工程化基线缺失**：补 eslint/pretier、最小测试（见 QA）、CI（install→lint→test→build→迁移 dry-run）、把 Vercel 与 GitHub 接通（当前 push 不触发自动部署，靠 CLI 手动 `vercel --prod`，容易漏发/错发）。

### 3.4 P2 — 可复现性与整洁度
- **地理编码不可复现**：Nominatim/Photon 在国内网络不通（lessons 17），当前靠浏览器在高德手点（成功率约 95%，8 家缺坐标）。建议封装一个 browser-use 高德批量地理编码脚本入 `food_pipeline`，输入"店名+地址"输出坐标+来源，可重跑、留痕，替代人工点。
- **工作区整洁**：根目录散落 14+ 个 `integrate_*.py`、`data_subagent_work/`、`data/backups/pipeline_work/` 等一次性产物。建议归档到 `archive/`（不进 git）或删除，管线唯一入口收敛到 `scripts/food_pipeline/`。
- 文档口径小冲突：lessons 19 写 status 为 active+"关店"，而 002/common 实际口径是 active/**closed**；应以 closed 为准统一文档。

## 7. 数据覆盖归因：为什么日料店"多"、其他菜系"少/浅"，以及对齐方案

> 结论先行：**不是店数问题**（川菜 101、粤菜 170 都多于日料 75），而是**细分网格深度与证据厚度的机制差异**。

### 7.1 实测对比（stage6，2026-09-22）
| 菜系 | 店数 | 细分叶子数 | 叶挂店中位 | 证据字中位 | 证据<200字店数 |
|---|---|---|---|---|---|
| 日料 | 75 | **15**（烹饪形式） | 5 | **380** | 0 |
| 川菜 | 101 | 5（仅地域） | **14（过密=粗）** | **69** | **83** |
| 粤菜 | 170 | 5 | 14 | 329 | 7 |
| 苏菜 | 80 | 5 | 11 | 230 | 28 |
| 浙菜 | 70 | 5 | 11 | 244 | 18 |
| 越餐/美餐/俄餐 | 15/26/8 | 4/5/3 | **2（浅）** | 356/372/359 | 0 |
| 本帮菜 | 19 | **0（未细分）** | — | 320 | 0 |

全库：空格 0、**薄格（1-2 家）21**、薄证据集中在川菜/苏菜/浙菜；电话覆盖率国际菜最低（中亚 12%、印度/越餐 20%、泰餐 35%、日料 44%）。

### 7.2 机制根因
- 日料是早期样板，按"**烹饪形式 × 档位**"双轴穷举、每格 3-10 家、档位符合品类常识（寿司含奢华、拉面全平价、怀石全奢华），并经历多轮人工点名补漏，证据厚。
- 其他菜系后期按"**菜系总量配额**"（热门 15-25 / 中等 8-15 / 小众 5-10）由多代理批量快采：
  - 中餐只按地域切 3-5 个叶子、每格堆 10-14 家——**缺"品类/店型"第二轴**（火锅/串串/烧腊/早茶/粥粉面/牛肉锅/小吃/宴席…），所以"粗"；
  - 国际/地方菜拆了叶子却每格 1-2 家种子就收尾——"浅"；
  - 配额没规定证据厚度，川菜 83% 店证据不足 200 字——"薄"，读起来就和点评罗列没区别。
- 旧管线 stage1-5 只校验**单条记录是否合法**，没有**结构性覆盖门**，所以粗/浅/薄在管线里隐形、能一路"合格"入库。

### 7.3 对齐方案（已固化进 skill 与新脚本，本轮完成）
1. **配额单位从"菜系"改为"网格里的格"**：供给充足叶子精选 ≥5 且覆盖 ≥2 档；一般 ≥3；确属稀缺 ≥2 并标注"供给稀缺"；禁止 1 家种子收尾；候选池=精选×2。
2. **细分轴因菜系而异**：日料/西餐/亚洲菜单轴（烹饪形式或国别×形式）；**中餐必须双轴（地域子流派 × 品类/店型）**，八大第二轴清单已写入 `cuisine-map.md`；场景类（咖啡甜品/brunch/bistro/酒吧）走形式/食材标签轴。
3. **证据厚度硬门**：`evidence_summary` ≥200 字、≥2 条含菜名堂食点评、≥2 类独立渠道，薄证据打回重采。
4. **新增 stage6 覆盖质量门**：`stage6_coverage.py` 只读审计"叶子×档位"网格，输出空格/薄格/薄证据/电话率与 `coverage-tasks.json`（本轮已生成 **26 项深采任务**）；收工闸门=无空格、薄格率<20%、薄证据<10%。微观 stage4、宏观 stage6，双门并守。
5. 已更新 skill：`data-pipeline.md`（七阶段 + §2.0 网格配额）、`cuisine-map.md`（统一深度标准 + 中餐品类第二轴）、`SKILL.md`（工作流/自检/引用）、`lessons-learned.md`（教训 21、22）。
