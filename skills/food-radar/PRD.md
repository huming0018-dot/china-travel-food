# food-radar PRD

> 版本 v1.2 ｜ 更新 2026-10-17 ｜ 状态：核心通路已跑通，处于"个人可用"阶段

## 一、问题

本地餐饮情报判断上有三个反复踩的坑：

1. **旧文章冒充新店**——2026-10 搜到一篇 2024-10 的文章，误把「攏好粵菜」列为当月新开，而该店 2024 年已退出上海。
2. **上榜 ≠ 在营**——榜单荣誉常被当作"还开着"的证据。
3. **拿不到数据却填数字**——评分/人均等精确值缺失时容易估算或留空而不声明。

## 二、目标

给 AI 一个**可复用的餐饮情报调研规程**：怎么查、怎么核实、怎么输出，以及拿不到数据时怎么如实声明。

**成功标准**：换城市、换品类复用时框架不变，只改关键词矩阵与本地信源清单。

## 三、范围

### 在范围内
- 调研框架：五步法 + 时效/信源校验 + 字段规范
- 三平台采集：小红书、抖音、大众点评
- 结构化输出：JSON + 人类可读摘要
- 产出物使用说明

### 明确不在范围内
- **定时调度与增量去重系统**——文档里的「每日雷达」目前只是 prompt 模板，**没有**任何调度器、去重逻辑或状态存储。这是当前最大的功能缺口。
- 大规模/高频抓取、商业用途
- 各平台的账号体系、订阅管理

## 四、约束

| 约束 | 来源 |
|---|---|
| 仅学习研究，不商用、不大规模爬取 | MediaCrawler 许可 |
| 登录态 cookie 只存本地，不进仓库不进交付物 | 安全 |
| 拿不到的数据填 `null`，禁止编造 | 铁律 |
| 不规避平台风控机制 | 合规边界 |

## 五、平台能力与前提

| 平台 | 通路 | 前提 |
|---|---|---|
| 小红书 | MediaCrawler `xhs` | 首次扫码，登录态持久化 |
| 抖音 | MediaCrawler `dy` | **需 Node**（execjs 依赖 Nashorn，JDK15+ 已移除，装 Java 无效） |
| 大众点评 | `scripts/dianping_fetch.py` | headful + 一次人工登录 + 持久化 profile |
| B站/海外 | agent-reach | 免登录 |
| 微信公众号 | wechat-article-search | 需 Node |

## 六、验收标准

1. 跑 `bash scripts/preflight.sh` 无阻塞项
2. 三平台均能采到数据且**有数据落盘**（不以"cookie 非空"为准）
3. 输出 JSON 符合 `field-spec.md`，必填字段齐全、枚举正确
4. 所有 `new_opening`/`open` 条目完成闭店核查
5. 每条结论带 `sources[]` + `confidence`
6. 交付物附使用说明

## 七、已知缺口（2026-10-17）

| 缺口 | 影响 | 状态 |
|---|---|---|
| 无定时调度 + 增量去重 | 「每日雷达」无法自动运行 | **未做** |
| 平台覆盖不完整 | 微博/快手/贴吧等未接入 | 未做 |
| 点评无增量接口 | 每跑一次都是全量搜索 | 设计受限 |
| preflight 版本号硬编码 | 换 Playwright 版本会误报 | 已知，未修 |
| 解析器基于正则 | 点评改版即失效 | 已知，需改为 DOM 选择器 |
| keyword-matrix 写死上海/2026 | 换城市需手改 | 已知，未修 |

## 八、后续优先级建议

1. **P0** 建增量机制：按 `note_id`/`shop_id` 去重 + 状态存储，否则无法做真正的持续监控
2. **P0** 点评解析器从正则改为 DOM 选择器（正则对改版极脆）
3. **P1** 关键词矩阵与城市/年份解耦
4. **P1** 接入微博/快手/贴吧
5. **P2** 定时调度（依赖 P0）
