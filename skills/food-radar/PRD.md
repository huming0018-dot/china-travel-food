# food-radar PRD v2 — 懂你口味的找店助手 + 餐饮新鲜事雷达

> v2.0 ｜ 2026-10-18 ｜ 形态：Skill／助手插件（不做独立 App）

## 一、定位转变

| | v1 调研工具 | v2 助手 |
|---|---|---|
| 触发 | 填一堆条件 | 自然语言一句话 |
| 输出 | 研究报告 | 一张卡片 |
| 流程 | 每次跑全链路、双信源强制 | 先快找，选中再深查 |
| 记忆 | 无 | 餐厅/活动/收藏/反馈分层存储 |
| 自动化 | 无（仅 prompt 模板） | 可选订阅，按需开启 |

## 二、三个入口

### 入口1 现在吃什么
> "我在静安寺，两个人，人均300，今晚想吃点特别的。"

优先维度：**距离 → 预算 → 营业时间 → 用餐场景**。
输出 3-5 家，每家说清：为什么选它、点什么、有什么缺点。
**必须分别标注三件不同的事**（见 §5）。

### 入口2 以后想吃什么
> "下个月去成都，帮我存几家值得专程去的。"

维护**想吃清单**：城市／菜系／预算／适合场景／想去原因／预订提前量／最近核验时间。
后续询问不必重新描述。

### 入口3 最近有什么新鲜事
> "上海未来一个月有什么飞行厨房、客座和新开店？"

强制分两栏：
- **新店**：即将开业／试营业／正式营业
- **限时活动**：飞行厨房／四手联弹／客座／快闪／限定菜单

每条限时活动必答：**谁来 · 在哪 · 哪天 · 多少钱 · 怎么订 · 是否还来得及**

## 三、记录层：餐厅与活动分离

| 类型 | 字段 |
|---|---|
| 餐厅档案 | 分店标识、位置、菜系、价位、招牌菜、适合场景、**营业状态** |
| 活动档案 | 举办餐厅、客座主厨、活动起止、**预订开放时间**、价格及包含项目、预订入口、**取消／售罄状态** |

活动是有期限、可能售罄、需独立更新的实体，**不是店铺简介里的一条备注**。
活动结束退出近期推荐，餐厅仍留在想吃清单。

## 四、流程：默认快找，决定前深查

**快找**：先搜公开信息 + 结合已有清单 → 短名单。没确认的地方直接写明，
**不因"某通路要登录"就整项停工**。

**深查**：用户选定后才重点查分店、近期菜单与价格、活动日期、订位入口、闭店／取消信息。

### 证据按问题类型分治

| 问题 | 首要证据 |
|---|---|
| 活动日期与价格 | 餐厅／主厨／主办方**公告** |
| 是否可订 | 订位页面时段 + **查询时间** |
| 实际好不好吃 | 近期食客反馈，**区分广告与不同口味** |
| 新开时间 | **区分文章发布日期与实际开业日期** |

**置信度落到具体字段**，不给整家店盖一个笼统的"可信"章。

## 五、硬约束（不可妥协）

1. **"正在营业 / 今日有位 / 无需排队"是三件不同的事，必须分别标注。**
   余位公开渠道查不到 → **"未确认"是一等状态**，宁可写未确认，也不为填满卡片而编造。
2. **组合无解时直接说无解。** 如"主厨驱动+米其林星级+周日午市+静安寺"，
   宁可回"今天没解"，也不硬凑平庸选项。
3. 拿不到的字段填 `null` + 说明原因，禁止估算。
4. 任何"智能兜底"都可能变成静默造假（v1.2.1 教训）。

## 六、输出形态：像助手

```
店名｜区域｜人均
为什么适合你：对应口味 + 本次场景
值得吃：招牌菜／限定菜单
注意：吵、难订、套餐限制等
时间与订位：活动日期、预订入口、余位是否确认
核验：何时查过 + 关键来源
```

**新鲜事额外一句**：为什么值得现在关注——例如"预订刚开放""客座只来两天"，
而非单纯搬运热度。

## 七、技术分层

| 层 | 职责 |
|---|---|
| Skill 层 | 识别意图（找店／收藏／查新鲜事），控制检索与输出 |
| 数据通路层 | 公开搜索优先；点评／小红书／公众号按需接入；失败时说明缺了什么 |
| 记录层 | 餐厅、活动、收藏、反馈；合并重复报道，识别同品牌不同分店 |

`preflight` 改为**按本次任务检查所需通路**，不是缺一个工具就全盘报废。

## 八、订阅（可选增强）

仅在用户明确要求后开启。只推：**新增 / 重要变更 / 临近截止**，不重复刷同一家店。

## 九、交付顺序与验收

| 阶段 | 内容 |
|---|---|
| **P1 先能用** | 即时找店 + 未来活动搜索 + 带来源短名单 + 卡片输出 |
| **P2 再懂你** | 餐厅/活动结构化存储、想吃清单、吃过评价、群聊按人区分 |
| **P3 最后自动化** | 多平台补充、增量追踪、按需提醒 |

### 验收标准（不看抓取条数）
1. 能否**很快**挑出想吃的店
2. 活动有没有过期（过期必须显式提示）
3. 预订信息是否说清楚（含"未确认"标注）
4. **下次它还记不记得你想吃什么**

## 十、已知约束

| 约束 | 说明 |
|---|---|
| 跨平台同名不同店 | 点评有 `shop_id`，小红书无。**2026-10-18 实测撞上**：公开搜索称"ONCUE＝顺德菜"，点评实为**西餐 4.8分/¥1064**（虹口沙泾路）。策略：保留多来源不强行合并，冲突时标出让用户确认 |
| 余位不可查 | 订位接口不公开，见 §5.1 |
| 记录层存储未定 | P2 前需定 JSON schema（markdown 无法做合并与字段级时间戳） |
| 多用户隔离 | 当前记忆按项目路径隔离，群聊按人区分需额外 user key |
| 登录态会过期 | 2026-10-18 实测小红书登录态失效需重扫 → cookie 非空≠仍有效 |
