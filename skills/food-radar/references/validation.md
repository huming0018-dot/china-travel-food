# food-radar 校验规范（Validation Spec）

## 一、三条铁律（违反即返工）

1. **双信源+日期规则**：任何"新开/在营"结论必须有两个独立信源，且两个信源都带明确的当年（当前年度）日期。仅一个信源 → `confidence` 降为 medium 并标注待核实。
2. **发布日期核对规则**：引用任何文章前必须核对并记录其发布日期；禁止凭内容语感判断新旧。搜索引擎摘要不带年份时，必须打开原文确认。
3. **在营核查规则**：上榜/获奖 ≠ 在营。每家店交付前必须做一次闭店/退出核查（检索"店名+闭店/停业/退出"），有闭店信号的一律移入 `excluded` 并注明原因。

## 二、信源冲突裁决

冲突时按级别裁决：S（官方/官媒/榜单）> A（行业媒体/KOL）> B（UGC）> C（软文）。
同级别冲突：取日期新者；仍冲突 → 两个说法都写进 `notes`，`confidence` 降一级。

## 三、数值类信息规则

- 评分、人均、榜单年份：必须记录"来源平台+抓取日期"；拿不到填 null，禁止估算。
- 米其林/黑珍珠荣誉必须带年份（如"2026米其林二星"），往年荣誉注明"往年"。

## 四、交付前 Checklist（全部通过才可交付）

- [ ] 每家店/事件都有 ≥1 个 S 或 A 级信源
- [ ] 所有 `opened_date` 来自显式日期，无猜测
- [ ] 每家店做过闭店/退出核查
- [ ] `confidence=high` 条目均满足双信源规则
- [ ] C 级软文线索未被直接引用
- [ ] 所有假设（如对标物无法确认）已在输出开头向用户声明
- [ ] 精确数值均标注来源与抓取时间，无编造

## 五、失败案例登记（持续追加）

| 日期 | 案例 | 违反规则 | 后果 |
|---|---|---|---|
| 2026-10-16 | 攏好粤菜被列为"10月新开" | 违反规则2（2024-10文章误判为2026-10）+ 规则3（未做在营核查，实际2024年已退出上海） | 用户纠正后移出推荐位，沉淀为本规范 |
| 2026-10-17 | **dianping-crawler 依赖接口 `mapi.dianping.com/searchshop.json` 返回 403**，加浏览器 UA 仍然 | 未先验证接口有效性就投入环境搭建 | 才发现该 2017 年项目已完全失效，JDK/Maven 白装。**教训：拿到第三方爬虫，先 curl 它的核心接口验证存活，再决定是否搭建环境** |
| 2026-10-17 | MediaCrawler **CDP 模式三次尝试全部失败**（端口 9222 从未监听，`DevToolsLocalState` 从未生成） | 违反"依赖缺失时避免反复在不可行路径投入" | 浪费多轮往返。根因：Chrome 155 App-Bound Encryption + 136+ 限制默认 profile 调试端口。**教训：同类失败出现第 2 次就该换路径** |
| 2026-10-17 | 用户报告"小红书已登录"，但实测 `web_session` cookie **值为空、长度 0**，抓取零产出 | 以主观判断代替客观校验 | 日志显示 `Login failed`。**教训：登录态必须以 cookie 非空 + 有数据落盘为准，不能凭"用户说成功"或"浏览器里显示已登录"** |
| 2026-10-17 | 试图从 Chrome 提取 cookie 复用登录态 | 未先评估可行性 | Chrome App-Bound Encryption 使自动化提取不可行，且 `web_session` 为 HttpOnly 控制台也取不到。**结论：扫码是唯一可靠路径** |
| 2026-10-17 | AppleScript 向 macOS Calendar 添加 90 分钟提醒连续 4 种写法失败 | — | 事件建成但无提醒。**教训：跨应用自动化失败 3 次即改用人工路径（.ics 导入），不要陷在 API 细节里** |
