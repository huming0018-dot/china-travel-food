# food-radar 方法论

> 版本：v1.0（2026-10-16 沉淀，含真实踩坑复盘）

## 一、五步工作流

### Step 1 对标解码
用户给的对标物是最高价值的输入，必须先拆解再检索：
1. 识别对标物类型：单品店（如"头灶"= 中餐 omakase / 米其二星 / 主厨发办 / 高客单 / 提前数月预订）、合作事件（如"遇外滩×江"= 高端地方菜系 × 米其林/亚洲50佳餐厅联弹）。
2. 提炼可操作筛选维度：菜系路线、主厨履历、价位带、荣誉清单、玩法（联弹/客座/会员制）、稀缺性、可合作性。
3. 无法确认的对标物（如检索不到"永和遇外滩"）必须显式说明假设，不得默认。

### Step 2 关键词矩阵
`城市 × 品类 × 时间 × 事件类型` 四维组合：
- 时间词：2026、近3个月、近6个月、10月/9月
- 事件词：新开、首店、试营业、联弹、客座、快闪、晚宴、闭店、停业、退出上海
- 品类词：用户指定 + 对标同类 + 当季热门
- 每组至少产出 6-10 个查询，覆盖中英文表述差异。

### Step 3 多通路分级检索
信源分级（冲突时高级别赢）：

| 级别 | 信源 | 用途 |
|---|---|---|
| S | 官方公告、政府/官媒（上观、静安官媒等）、榜单官网 | 开业/闭店事实、榜单荣誉 |
| A | 权威行业媒体、KOL 长文（公众号、B站、微博大V） | 主厨背景、联弹事件、口碑描述 |
| B | 平台 UGC（大众点评、小红书、抖音评论） | 真实食客反馈、排队/订位难度 |
| C | 聚合软文、百家号种草 | 仅作线索，必须升级验证后才可引用 |

检索顺序：S 级定事实 → A 级补故事 → B 级验口碑 → C 级只用于发现线索。

### Step 4 时效与信源校验
见 `validation.md`，三条铁律：
1. "新开"必须双独立信源 + 均带当年日期。
2. 所有文章必须核对发布日期（不能凭内容语感判断新旧）。
3. 闭店/退出单独核查；上榜≠在营。

### Step 5 结构化输出与沉淀
- 按 `field-spec.md` 字段输出，每条带 sources 数组和 confidence。
- 交付后把本次的信源、踩坑、用户口径偏好沉淀进长期记忆，形成复利。

## 二、踩坑复盘（2026-10-16 真实案例）

| 坑 | 表现 | 根因 | 修复规则 |
|---|---|---|---|
| 攏好粤菜误列"10月新开" | 把 2024-10-31 的搜狐文章当成 2026-10 新店推荐 | 搜索引擎返回结果不带明显年份标识，"10月"字样被误读；且该店 2024 年已退出上海 | 规则：开业时间必须来自带完整发布日期的 S/A 级信源；交付前对每家店做一次"是否仍在营"核查 |
| "永和遇外滩"无法确认 | 用户给的对标物公开渠道检索不到 | 可能是内部合作/口误 | 规则：对标物无法验证时必须显式声明假设，请用户确认口径 |
| 微信搜狗搜索返回旧文 | 检索"上海新开餐厅"返回 2016-2023 文章 | 搜狗微信索引时效差、排序旧 | 规则：微信通路必须叠加时间词，且只采用带当年日期的结果 |
| 本机缺 Node | 微信文章搜索脚本无法运行 | 环境无 Node | 规则：开工先检查运行时依赖（node/python），缺则先装 |
| 点评/小红书站内数据拿不到精确值 | 只能拿 web_search 摘要里的 UGC 只言片语 | 无反公开 API | 规则：评分/人均等精确数据必须标注"来源平台+抓取时间"，拿不到就写 null，不得编造 |

## 三、可复用性说明

本方法论与品类、城市无关：换城市只换关键词矩阵与本地信源清单（如北京换"大众点评北京+京觅"类渠道，广州换"羊城攻略"类本地号）。工具链、校验规则、字段规范完全不变。
